# Правила для агентов

Читает каждый агент перед началом работы. Цель — параллельная работа без конфликтов и **без выдуманных чисел**.

## 1. Конвейер

```
Этап 0–1  bench-*    → bench/<свой модуль>/        адаптеры моделей, стенд, раннер
          models     → models/manifest.json        источники весов, хеши, конвертация
Этап 0–3  eval       → eval/                       метрики + тесты
Прогоны   runner     → results/raw/, logs/runs.md  сырые результаты и журнал
Анализ    analyst    → data/*.csv, docs/*_report.md агрегаты для статьи, отчёты
Сведение  coordinator→ STATUS.md, PLAN.md, git     (человек или основной агент)
```

## 2. Зоны ответственности

| Агент | Задача | Пишет ТОЛЬКО в |
|---|---|---|
| `bench-mediapipe` | адаптер BlazePose (MediaPipe Tasks) | `bench/adapters/mediapipe*`, `research/progress/bench-mediapipe.md` |
| `bench-tfjs` | адаптер MoveNet (TF.js) | `bench/adapters/tfjs*`, `research/progress/bench-tfjs.md` |
| `bench-ort` | адаптеры RTMPose/RTMO/YOLO (ONNX Runtime Web), конвертация | `bench/adapters/ort*`, `research/progress/bench-ort.md` |
| `bench-core` | страница стенда, общий интерфейс, раннер Playwright, страница для телефона | `bench/` (кроме `bench/adapters/`), `research/progress/bench-core.md` |
| `models` | загрузка/проверка весов, `manifest.json` | `models/`, `docs/models.md` |
| `eval` | метрики, отбор COCO, тесты | `eval/`, `docs/datasets.md`, `research/progress/eval.md` |
| `runner` | запуск прогонов | `results/raw/`, `logs/runs.md` |
| `analyst` | агрегаты, статистика, отчёты | `data/`, `docs/*_report.md` |
| `coordinator` | план, статус, git | `STATUS.md`, `PLAN.md`, `REQUIREMENTS.md`, `HANDOFF.md`, `README.md` |

Нельзя править чужие файлы. Предложения — в раздел «Вопросы и предложения» своего progress-файла.

## 3. Запись по ходу работы (обязательно)

Контекст ограничен, работа может оборваться. Поэтому:
1. Сделал шаг (адаптер заработал, прогон завершён, метрика посчитана) → **сразу** запиши в `research/progress/<агент>.md`: что сделано, команды запуска, версии, где результат, что не получилось.
2. Каждый прогон → строка в `logs/runs.md`: дата, ID прогона, модель, бэкенд, окружение, число изображений/замеров, файл результата, статус.
3. Новый агент начинает с чтения своего progress-файла и `STATUS.md`.

## 4. Правила для чисел

- Числа в отчётах и `data/*.csv` — только из реально выполненных прогонов, со ссылкой на файл в `results/raw/`.
- Нет данных → `TODO: нужны данные`. Не «оценивать на глаз», не переносить числа из статей в таблицы результатов.
- Окружение указывается всегда. Замеры скорости в облачном headless Chromium помечаются `env=desktop-headless` и **не** выдаются за результаты телефонов.
- Если число сильно расходится с опубликованным (например, AP ниже на > 10 пунктов) — сначала искать ошибку стенда (порядок точек, нормировка координат, порог), записать гипотезы в progress.

## 5. Код

- JS/TS для стенда (ES-модули, без сборщика на этапе 0; позже — Vite при необходимости); Python 3 для `eval/` (numpy, pycocotools), запуск с `-I` для чтения скачанных данных.
- Зависимости фиксируются (`package-lock.json`, `requirements.txt`).
- Веса, датасеты, видео — не коммитить (см. `.gitignore`). Малые сырые результаты (< 5 МБ) — можно.
- Скачанные файлы — в отдельные пустые каталоги (`models/cache/`, `datasets/`), скрипты — отдельно.
- Агенты не выполняют git-команды; коммиты делает координатор.

## 6. Связь со статьёй

Протокол — раздел 3 статьи `mobile-pose-article/sections/03_methods.md`. Итоговые CSV переносит координатор в `mobile-pose-article/data/`. Если в ходе работы протокол приходится менять — записать предложение в progress, координатор согласует с автором и обновит обе стороны.
